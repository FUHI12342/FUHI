# バックログ棚卸しと実装前検証

最終更新: 2026-09-01(改修ラウンド `claude/hardening-review-bok4kj` 時点)

未実装・検討中の項目を棚卸しし、実装前検証(必要性・設計案・工数・リスク)を行った結果。
判定は **次ラウンド採用 / 条件付き(判断待ち) / 保留 / 見送り** の4値。

## 次ラウンド採用(実装前検証を通過。着手可能)

### B-1. 役割ベース権限(店長ロール)
- **現状**: 店舗スタッフなら誰でも(キャスト含む)開店操作・SNS承認・発注承認ができる。
- **検証**: SNS承認・発注承認は金銭・対外影響のある操作であり、承認権限の分離は要件B-3/F-4の
  「人間の承認」の実効性に直結する。`Staff` に `is_manager` フラグを追加し、
  `user_belongs_to_store`(booking/access.py に集約済み)に `require_manager=False` 引数を
  足すだけで全アプリに波及できる構造になっている。
- **工数**: 小(フィールド1つ+判定1箇所+テスト)。
- **リスク**: 1人店舗では全員店長にすればよく、運用負荷は増えない。

### B-2. PostgreSQL(Cloud SQL)対応
- **現状**: SQLite 固定。Cloud Run はコンテナ再起動でローカルファイルが消えるため、
  **本番デプロイの前提条件**。
- **検証**: `DATABASE_URL` 環境変数での切替(dj-database-url 導入 or 手書きパース)。
  モデルは全て標準フィールドで Postgres 互換(部分UNIQUE制約・CheckConstraint も対応済み)。
- **工数**: 小。ただし Cloud SQL インスタンス作成はアカウント所有者の作業(external-setup-guide 参照)。

### B-3. エラートラッキング(Sentry 等)
- **検証**: SNS配信・GBP同期など外部API呼び出しの失敗はチェックリスト警告に載るが、
  想定外の500はログにしか残らない。本番運用開始と同時に導入すべき。
- **工数**: 小(SDK導入+DSN環境変数)。

## 条件付き(ユーザーの判断・情報が必要)

### C-1. 深夜営業(閉店が翌日にまたがる営業時間)対応
- **現状**: `closing_hour <= 24` を DB 制約で強制(18時-翌2時は登録不可)。
  レビューで「ナイト系業態で 18-26時 が入力されると全カレンダーが500になる」問題として検出し、
  暫定対応として制約で入口を塞いだ。
- **設計案**: `closing_hour` を最大30(=翌6時)まで許可し、カレンダー・座席ボードは
  `hour % 24` で描画、`make_aware_datetime` は 24以上で翌日に繰り上げ。
  影響範囲: booking(カレンダー2画面・座席ボード)、operations(BusinessDay override 検証、
  GBP specialHours の日跨ぎ表現)、sns(文面の営業時間表記)。
- **工数**: 中。**実店舗の実際の営業時間が判明してから着手**(占い業態なら不要)。

### C-2. 顧客向け座席予約UI(飲食業態)
- **現状**: 顧客が予約できるのはスタッフ時間枠のみ。座席割当は店側(admin/座席ボード)。
- **検証**: 飲食業態で「人数→空き座席の自動候補」を顧客に開放する場合、
  ノーショー対策(確認メール等)とセットでないと空予約リスクがある。
- **工数**: 中。**実運用の予約導線(電話中心か、Web中心か)が判明してから**。

### C-3. X への画像添付投稿
- **現状**: X はテキストのみ(v2 /tweets)。画像は media upload エンドポイントの追加実装が必要。
- **検証**: X の契約プラン(無料/Basic)によって media upload の可否・上限が変わるため、
  **プラン契約の判断後に**実装するのが手戻りがない。
- **工数**: 小〜中。

### C-4. 発注書PDF出力(FAX運用向け)
- **検証**: 現状の発注書テキスト+メールで大半の仕入先はカバーできる。
  FAX送信が実際に必要な仕入先が存在するかを確認してから(reportlab 導入で1日以内)。

## 保留(害はないが優先度が低い)

- **H-1. 開店処理の排他制御強化**: 二重クリックで `open_store` が並行実行され得るが、
  受け側処理(get_or_create / update)は冪等で実害は限定的。PostgreSQL 移行時に
  `select_for_update` で対応するのが自然(SQLite ではロック粒度が粗く効果が薄い)。
- **H-2. チェックリスト完了率・営業日レポート**: データは揃っている(done_at/done_by)。
  運用が回り始めてから要望ベースで。
- **H-3. 在庫の棚卸しモード画面**: 現状は admin の StockMovement(棚卸補正)で代替可能。
- **H-4. SNS投稿のプレビュー画像のプラットフォーム別最適化**(ストーリーズ比率等): 効果検証後。

## 見送り(実装前検証で棄却。要件定義書 §4 の R-1〜R-8 に追加)

- **R-9. Instagram 画像の署名付きURL化**: IG のコンテナ作成は非同期で画像を取得するため、
  短命の署名URLは取得失敗リスクがある。公開バケット+推測困難なファイル名の現行方式を維持。
- **R-10. 承認済みSNS下書きの「作り直し(取り下げ→再投稿)」**: プラットフォーム側の
  投稿削除APIまで実装しないと不整合になる。誤投稿時は各SNSで手動削除する運用とし、
  システムは同日の重複投稿をDB制約で防ぐところまでを責務とする。
