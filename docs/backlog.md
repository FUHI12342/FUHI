未実装・検討中の項目を棚卸しし、実装前検証(必要性・設計案・工数・リスク)を行った結果。

## 次ラウンド採用 → ✅ 実装済み(2026-09-01)

### B-1. 役割ベース権限(店長ロール) — ✅ 実装済み
- `Staff.is_manager` を追加し、承認系操作(SNS承認・発注承認/取消/入荷・開閉店・勤怠CSV)を
  `user_belongs_to_store(..., require_manager=True)` でゲート。閲覧・チェックリスト・打刻・
  下書き生成・発注案生成は全スタッフのまま。権限マトリクスは operations-model.md 参照。

### B-2. PostgreSQL(Cloud SQL)対応 — ✅ 実装済み
- `DATABASE_URL` 環境変数で切替(project/database.py。TCP と Cloud SQL Unix ソケット両対応、
  依存追加なしの自前パーサ+単体テスト)。psycopg[binary] を requirements に追加。
  Cloud SQL インスタンス作成はアカウント所有者の作業(external-setup-guide 参照)。

### B-3. エラートラッキング(Sentry) — ✅ 実装済み
- `SENTRY_DSN` 設定時のみ有効。`send_default_pii=False`(予約者名・キャスト名を送らない)。
- あわせて `check --deploy` の警告を解消(本番の HTTPS 強制・secure cookie・HSTS 1時間。
  HSTS preload/includeSubDomains はドメイン運用確定まで意図的に見送り)。

### C-1. 深夜営業(閉店が翌日にまたがる営業時間)対応 — ✅ 実装済み(2026-09-01)
- `closing_hour` を最大30(=翌6時)まで許可(例: 18時-翌2時 → 18, 26)。営業24時間超は
  枠の帰属が曖昧になるため DB 制約で禁止。
- カレンダー・座席ボードは 25時・26時のナイト業態慣習表記で行が伸び、翌日早朝の予約は
  `Store.business_slot()` により前営業日の枠として表示・予約できる(hour≧24 の予約URLは
  翌日早朝の実時刻に変換して保存)。GBP specialHours も endDate 翌日で日跨ぎ対応。
- 閉店24時以内の店舗には挙動変更なし。ユーザー回答を待たず安全に導入できると判断して実装した。

## 条件付き(ユーザーの判断・情報が必要)

### C-2. 顧客向け座席予約UI(飲食業態)
- **現状**: 顧客が予約できるのはスタッフ時間枠のみ。座席割当は店側(admin/座席ボード)。
- **検証**: 飲食業態で「人数→空き座席の自動候補」を顧客に開放する場合、
  ノーショー対策(確認メール等)とセットでないと空予約リスクがある。
- **工数**: 中。**実運用の予約導線(電話中心か、Web中心か)が判明してから**。

### C-3. X への画像添付投稿
- **現状**: X はテキストのみ(v2 /tweets)。画像は media upload エンドポイントの追加実装が必要。
- **検証**: X の契約プラン(無料/Basic)によって media upload の可否・上限が変わるため、
  **プラン契約の判断後に**実装するのが手戻りがない。
- **工数**: 小〜中。

### C-4. 発注書PDF出力(FAX運用向け)
- **検証**: 現状の発注書テキスト+メールで大半の仕入先はカバーできる。
  FAX送信が実際に必要な仕入先が存在するかを確認してから(reportlab 導入で1日以内)。

## 見送り(実装前検証で棄却。要件定義書 §4 の R-1〜R-8 に追加)

- **R-9. Instagram 画像の署名付きURL化**: IG のコンテナ作成は非同期で画像を取得するため、
  短命の署名URLは取得失敗リスクがある。公開バケット+推測困難なファイル名の現行方式を維持。
- **R-10. 承認済みSNS下書きの「作り直し(取り下げ→再投稿)」**: プラットフォーム側の
  投稿削除APIまで実装しないと不整合になる。誤投稿時は各SNSで手動削除する運用とし、
  システムは同日の重複投稿をDB制約で防ぐところまでを責務とする。
