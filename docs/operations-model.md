# 運用想定(オペレーションモデル)

最終更新: 2026-09-01

システムが想定する日々の運用フロー・役割分担・障害時のフォールバックを定義する。
新しいスタッフへの説明資料としても使えるように書く。

## 1. 役割と権限マトリクス

| 操作 | スーパーユーザー | 店長(is_manager) | スタッフ・キャスト | 備考 |
|---|---|---|---|---|
| 開店・閉店操作 | ✅ | ✅ | ─ | 開店で自動処理(SNS下書き・品出しタスク等)が連鎖 |
| チェックリストのチェック | ✅ | ✅ | ✅ | 全員で消し込む |
| SNS投稿の閲覧・再生成 | ✅ | ✅ | ✅ | 生成は何度でも安全(承認済みは上書き不可) |
| **SNS投稿の承認(=投稿)** | ✅ | ✅ | ─ | 対外影響があるため店長限定 |
| 座席ボード・着席/離席 | ✅ | ✅ | ✅ | |
| 入荷登録・発注案の生成 | ✅ | ✅ | ✅ | 発注案生成は下書きなので全員可 |
| **発注の承認・取消・入荷済み** | ✅ | ✅ | ─ | 金銭影響があるため店長限定 |
| 自分の打刻 | ✅ | ✅ | ✅ | 他人の打刻は不可 |
| 勤怠CSVエクスポート | ✅ | ✅(自店舗のみ) | ─ | 給与SaaSへ渡す |
| マスタ管理(admin) | ✅ | ─ | ─ | 座席・商品・テンプレ・シフト登録 |

- 店長権限は admin の「スタッフ」画面で `店長(承認権限)` にチェックして付与する。
- 退職時は `在籍中` を外す(SNS掲載と勤怠画面から自動的に消える。削除はしない)。
- 顔出しNGのキャストは `SNS掲載可` を外す(文面・画像の両方から除外される)。

## 2. 日次運用フロー

### 開店前(店長 or 早番スタッフ)
1. `/ops/store/<id>/today/` を開く → 当日の営業日とチェックリストが自動生成される
2. 臨時の営業時間変更がある日は admin の「営業日」で臨時開店/閉店時刻を入れる
3. 当日シフトに欠勤が出たら admin の「シフト」で状態を「欠勤」に変更
   (欠勤者はSNS文面から自動的に消える — **開店前に必ず反映すること**)
4. 商品が届いていたら在庫画面(`/inventory/store/<id>/`)で入荷登録
   (SNS告知対象📣の商品はこの入荷が当日のSNS文面「入荷情報」に載る)

### 開店操作(店長)
5. ダッシュボードの「開店する」を押す。自動で:
   - 当日シフトが「確定」になる
   - SNS下書き(文面+画像)が生成され、チェックリストに「SNS投稿を承認する」が載る
   - 品出しタスク(本日入荷分)と在庫僅少の警告タスクが載る
   - 臨時営業時間がある日は GBP 自動反映 or 手動更新リマインダー
   - **自動処理が失敗しても開店は完了する。失敗は赤い警告としてチェックリストに出るので、
     チェックリストを上から消し込めば取りこぼしはない**
6. SNS画面で下書きを確認 → 問題なければ「承認して投稿する」
   - API設定済み: 自動投稿され、投稿URLが記録される
   - API未設定/失敗: 「手動投稿してください」と表示 → 文面と画像をコピペ投稿
   - 失敗したプラットフォームは「再配信」ボタンで再試行できる(二重投稿はしない)

### 営業中(全スタッフ)
7. 座席ボードでウォークインの着席/離席を記録。予約は従来のカレンダーから
8. 出勤時・退勤時に `/attendance/` で打刻

### 閉店(店長)
9. ダッシュボードの「閉店する」を押す
10. 発注案があれば内容を確認して承認(メール送信 or 発注書テキストをLINE/FAX)

### 週次・月次(店長)
- 週1回程度: 在庫の実数と画面の数字を突合し、ズレは admin の「棚卸補正」で修正
- 発注品が届いたら発注詳細の「入荷済みにする」を押す(在庫に自動反映+再提案が解禁される)
  - 押し忘れても30日で再提案は自動復活する(安全弁)
- 月初: 前月の勤怠CSVをエクスポートして給与計算SaaSへインポート

## 3. 障害・例外時のフォールバック

| 事象 | システムの挙動 | 人間の対応 |
|---|---|---|
| SNS API 障害・トークン失効 | 該当プラットフォームだけ「失敗」記録。他は継続 | 文面コピペで手動投稿 → 復旧後は「再配信」 |
| 画像生成の失敗 | 開店は完了し、警告タスクが出る | 「再生成」を押す。ダメなら文面のみ投稿 |
| 発注メール不達 | ─ | 発注書テキストを電話/FAX/LINEで送付 |
| GBP API 未承認・障害 | リマインダータスクに格下げ | Googleマップアプリから手動更新 |
| 在庫記録が現実とズレた | 発注案が不正確になる | 棚卸補正で修正。発注承認前に必ず数字を目視 |
| 誤ってSNS承認した | システムからの取り消しは不可(見送り済み) | 各SNSアプリから手動削除 |
| サーバ障害 | ─ | 開店業務は紙のチェックリストで代替可能な設計。
SNSは手動投稿、予約は電話台帳で一時運用 |

## 4. 監視・保守

- **CI**: push ごとに全テスト実行(GitHub Actions)。赤のまま main にマージしない
- **エラートラッキング**: `SENTRY_DSN` を設定すると本番の想定外エラーが通知される
  (個人情報は送信しない設定済み)
- **チェックリスト警告**: 自動処理の失敗は必ずチェックリストに出る。
  「警告付きタスクが残ったまま閉店しない」を運用ルールにする
- **月1メンテ**: `pip list --outdated` の確認、Django セキュリティリリースの適用

## 5. 想定していない使い方(やらないこと)

- 無人でのSNS確定投稿・無人での発注確定(必ず店長の承認を挟む)
- 営業24時間超の営業時間登録(深夜営業は翌6時=30時まで対応。18時-翌2時は「18」「26」と登録)
- 顧客自身による座席指定予約(backlog C-2。現状は店側が割り当てる)
- システム上での給与計算(勤怠CSVをSaaSに渡すまでが責務)
