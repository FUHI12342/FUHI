# 開店業務自動化 拡張要件定義書・実装計画

対象システム:占い・飲食店予約管理システム(本リポジトリ `django-booking-sample`)
目的:リアル店舗の開店業務を自動化・半自動化する機能群を要件として定義し、
「実装済み / 実装済みだが改修推奨 / 新規構築」に分類したうえで、
敵対的レビュー(実現可能性・費用対効果・運用リスクの観点からの反証)を通過したものだけを実装計画に載せる。

---

## 1. 現状分析(既存資産の棚卸し)

リポジトリに存在する実装は以下のみ。

| 資産 | 内容 | 状態 |
|---|---|---|
| `Store` モデル | 店舗(店名のみ) | 実装済み |
| `Staff` モデル | 店舗スタッフ(ログインユーザー紐付け) | 実装済み |
| `Schedule` モデル | スタッフ単位・1時間刻みの予約枠 | 実装済み |
| 予約カレンダー(`StaffCalendar` / `Booking`) | 週間カレンダー表示と空き枠予約 | 実装済み |
| マイページ(`MyPage*`) | スタッフ自身の予約確認・変更・削除・休暇登録 | 実装済み |
| テスト(`booking/tests.py`) | ビュー中心に約500行 | 実装済み |

**SNS投稿・Googleマップ連携・勤怠・座席・在庫に関する実装は一切存在しない。**
今回の拡張のほぼすべてが「新規構築」であり、既存部分は「改修推奨」に該当する。

### 1.1 既存実装の改修必須事項(拡張の前提となる負債)

| # | 問題 | 根拠 | 改修内容 |
|---|---|---|---|
| P-1 | Django 2.2(EOL済み、セキュリティパッチ提供終了) | `project/settings.py` ヘッダ、`Pipfile` | Django 5.x LTS へアップグレード |
| P-2 | `SECRET_KEY` がリポジトリにコミットされている | `project/settings.py:23` | 環境変数化・キーローテーション |
| P-3 | `DEBUG = True` 固定、`ALLOWED_HOSTS` 空 | `project/settings.py:26-28` | 環境変数による本番/開発切替 |

| P-5 | `USE_TZ = True` なのに naive datetime を生成・比較している(予約作成とカレンダー抽出が JST/UTC 境界でずれる) | `views.py` の `Booking.form_valid`、`StaffCalendar` の `start_time`/`end_time` | `timezone.make_aware` に統一 |

## 2. 機能要件と評価

各機能を「要件 → 分類 → 敵対的レビュー → 判定」の形式で定義する。
判定は **採用 / 条件付き採用 / 見送り** の3値。見送りは §4 に集約。

### A. 開店業務基盤(開店チェックリスト・営業日管理)

すべての自動化のハブとなる基盤。他機能(SNS投稿・GBP更新・品出し)はここから連鎖起動する。

**要件**
- A-1: `BusinessDay`(営業日)エンティティ。日付・店舗・営業時間(臨時変更含む)・状態(準備中/営業中/閉店)を持つ。
- A-2: 開店チェックリスト。テンプレートから当日タスクを自動生成(清掃、レジ開け・釣銭確認、品出し、看板出し、SNS投稿確認 等)。担当者がスマホでチェック。
- A-3: 「開店」操作をトリガーに自動処理を連鎖実行(SNS投稿キュー投入、GBP営業時間確認、当日シフト確定)。失敗タスクはチェックリスト上に警告表示。

**分類**:新規構築

**敵対的レビュー**
- 「チェックリストは紙で十分では?」→ 紙ではSNS投稿・GBP更新の実行結果と連動できない。自動処理の失敗を人間が検知する場所として必須。反証不成立。
- 「状態機械が複雑化しないか?」→ 状態は3値に限定し、タスクは冪等に設計する(再実行安全)。過剰設計を避けるため承認フロー等はここには持たせない。

**判定:採用**(全自動化機能の前提。Phase 1)

---

### B. SNS自動投稿(X / Instagram / Threads)

**要件**
- B-1: 投稿文面の自動生成。当日シフト(D)から出勤キャスト一覧、在庫(F)から入荷情報を差し込むテンプレートエンジン(店舗ごとに文面テンプレを管理画面で編集可能)。
- B-2: 投稿画像の自動生成。キャストのプロフィール画像+店舗テンプレ(ロゴ・日付・出勤者名)を Pillow で合成。キャストごとに「画像使用可否フラグ」を持つ(顔出しNG対応)。
- B-3: **下書き→店長承認→投稿**のワークフロー。無人での自動確定投稿は行わない。承認はスマホの管理画面からワンタップ。
- B-4: プラットフォーム別アダプタ:
  - Threads:公式 Threads API(テキスト+画像投稿に対応)
  - Instagram:Instagram Graph API(ビジネスアカウント必須。画像は公開URL経由でのみ投稿可能なため、Cloud Storage の署名付き/公開URLを使用。Meta アプリレビュー通過が前提)
  - X:API v2。無料枠は投稿数制限が厳しく仕様変更が頻繁なため、有料 Basic プランを予算計上するか、失敗時は「文面+画像を生成して手動コピペ投稿」にフォールバック
- B-5: 投稿結果(成功/失敗/投稿URL)を営業日(A)に記録。失敗時は開店チェックリストに警告。

**分類**:新規構築

**敵対的レビュー**
- 「完全自動投稿にすべきでは?」→ 誤投稿(退職済みキャスト掲載、顔出しNG画像、誤った入荷情報)は営業被害・人格権侵害に直結する。**承認フロー必須を採用条件とする**。文面・画像の生成までが自動、確定は人間。
- 「X API は信頼できるか?」→ 料金・仕様変更が頻繁で、無料枠では実用に耐えない可能性が高い。**X はフォールバック(手動コピペ用生成物の出力)を必須要件に含めることを条件に採用**。API が使えなくても機能全体は価値を保つ設計にする。
- 「Instagram のアプリレビューに落ちたら?」→ レビュー通過まで数週間かかる場合がある。Threads(審査が軽い)→ X → Instagram の順に段階リリースし、Instagram は通過するまで手動フォールバックで運用。
- 「3プラットフォーム同時対応は過剰では?」→ アダプタパターンで共通の投稿キューに載せるため、追加コストはプラットフォームあたりの認証+API呼び出しのみ。共倒れしない設計であれば過剰ではない。

**判定:条件付き採用**(承認フロー必須・全プラットフォームに手動フォールバック必須。Phase 2)

### C. Googleマップ情報の自動化(Google ビジネスプロフィール / GCP)

「GCP」は (1) Google ビジネスプロフィール(GBP、Googleマップ掲載情報)の自動更新、(2) 実行基盤としての Google Cloud Platform、の両解釈で要件化する。

**要件**
- C-1: GBP 営業時間の自動同期。営業日(A)の臨時休業・営業時間変更を Business Profile API 経由で反映。
- C-2: GBP への「最新情報」投稿。SNS投稿(B)と同じ生成物を GBP のローカル投稿としても配信(同一承認フローに載せる)。
- C-3: 実行基盤:Cloud Run(Django + ワーカー)、Cloud Scheduler(開店前ジョブの起動)、Cloud Storage(投稿画像・キャスト画像)、Secret Manager(APIキー)。
- C-4: GBP のクチコミ新着通知を管理画面に表示(返信は人間が行う)。

**分類**:新規構築

**敵対的レビュー**
- 「Business Profile API は使えるのか?」→ API 利用は Google への申請承認制であり、個人・小規模事業では承認されないことがある。また業種(占い・ナイト系)によっては掲載ポリシー上の制約を受ける可能性がある。**API 承認が取れることを採用条件とし、取れない場合 C-1/C-2/C-4 は見送り、管理画面に「GBPで手動更新すべき項目」のリマインダー表示に格下げする**。
- 「Googleマップに空席状況をリアルタイム表示できないか?」→ そのような一般開放 API は存在しない。予約導線の掲載(Reserve with Google)は認定予約プロバイダ経由のみで、単独店舗が直接参加することは現実的に不可能。**見送り(§4)**。
- 「GCP は過剰では? VPS で十分?」→ Cloud Run は最小構成なら月数百〜数千円で、Scheduler・Secret Manager 含め運用負荷が VPS より低い。SNS 画像の公開 URL 要件(B-4)にも Cloud Storage が直接応える。反証不成立。

**判定:C-3 採用(Phase 1 でインフラとして先行)/ C-1・C-2・C-4 条件付き採用(API承認取得が条件。Phase 3)**

---

### D. キャスト・スタッフ勤怠管理

**要件**
- D-1: シフト計画。日付×スタッフ×時間帯の出勤予定を管理者が登録、スタッフ本人が希望提出。**当日の確定シフトが SNS 投稿(B-1)の「出勤キャスト」の唯一のデータソースになる**。
- D-2: 出退勤打刻。スマホからの打刻(店舗Wi-Fi/位置情報による簡易検証)。予定と実績の突合表示。
- D-3: 勤務実績の月次 CSV エクスポート(給与計算 SaaS へのインポート用)。
- D-4: 既存 `Staff` モデルの拡張:表示名に加え、キャスト区分、プロフィール画像、SNS掲載可否フラグ、在籍状態。

**分類**:D-4 は既存 `Staff` の改修、D-1〜D-3 は新規構築

**敵対的レビュー**
- 「勤怠は SaaS(ジョブカン、KING OF TIME 等)を使うべきで自前実装は車輪の再発明では?」→ **半分正しい**。給与計算・残業36協定・有給管理・労基法対応まで自前で作るのは工数対効果が最悪で、法改正追従の保守コストを永久に負う。**この層は自前構築を見送り(§4)、CSV エクスポート(D-3)で SaaS に接続する**。一方、シフト(D-1)は SNS 投稿・座席・チェックリストと連動する本システムのコアデータであり、外部 SaaS からリアルタイムに取り出す API 連携のほうがむしろ高コスト。シフト+打刻のライト層のみ自前が合理的。
- 「打刻の位置情報検証は必要か?」→ 小規模店では店長の目視で足りる。GPS 検証は「あれば使う」程度のオプションとし、必須要件から外す(過剰要件の排除)。

**判定:採用(シフト+打刻+CSVのライト勤怠に限定。給与・法令対応層は見送り)**(Phase 1)

---

### E. 座席・予約状況による管理

**要件**
- E-1: `Seat`(座席/テーブル)モデルの新設。店舗×座席名×定員×種別(カウンター/テーブル/個室/占い鑑定席)。
- E-2: 予約への座席割当。既存 `Schedule` を拡張し、任意で座席を紐付け。同一時間帯の同一座席の重複割当を DB 制約で禁止。
- E-3: 当日の座席ボード。時間帯×座席のグリッドで予約・ウォークイン(飛び込み)・空席を一覧。ウォークインは着席/離席のワンタップ記録。
- E-4: 既存予約フローの改修(§1.1 P-5〜P-7:タイムゾーンバグ、営業時間ハードコード、二重予約競合)。
- E-5: 占い店舗(スタッフ指名・時間枠)と飲食店舗(座席・人数)の両モードを `Store` の業態フラグで切替。

**分類**:E-4 は実装済みだが改修推奨、E-1〜E-3・E-5 は新規構築

**敵対的レビュー**
- 「グルメサイト(ホットペッパー等)の予約在庫と連携すべきでは?」→ 在庫連携 API は一般開放されておらず、サイトコントローラー契約は月額コストと審査を要する。個店規模では費用対効果が合わない。**見送り(§4)**。自社サイト・電話・LINE 経由の予約を本システムの台帳に一元記録する運用に絞る。
- 「座席の自動最適割当(パズル最適化)は?」→ 個店の座席数(十数席)では店長の手動割当のほうが速く正確。実装コストに見合わない。**見送り(§4)**。空きの可視化と重複防止までがシステムの仕事。
- 「既存 Schedule を捨てて作り直すべきか?」→ 既存はスタッフ枠予約として機能しておりテストも存在する。P-5〜P-7 の改修+座席の追加拡張のほうがリスクが低い。作り直しの反証は不成立。

**判定:採用**(E-4 の改修は Phase 0、新規分は Phase 1〜2)

### F. 品出し・在庫状況・自動発注

**要件**
- F-1: 商品マスタ(品名、カテゴリ、仕入先、発注点、発注ロット)。
- F-2: 入出庫記録。入荷・販売消費・廃棄をスマホから記録し、現在庫を算出。日次の実地棚卸で補正。
- F-3: 品出しタスク連動。発注点を下回った/入荷した商品を開店チェックリスト(A-2)の品出しタスクに自動反映。
- F-4: **発注案の自動生成+人間承認**。現在庫が発注点を下回った商品から発注案(仕入先別にグルーピング)を自動生成し、店長がワンタップ承認すると仕入先へメール送信、または LINE/FAX 用の発注書 PDF を出力する。
- F-5: 入荷情報を SNS 投稿(B-1)の「入荷情報」差し込みデータとして提供(商品ごとに「SNS告知対象」フラグ)。

**分類**:新規構築

**敵対的レビュー**
- 「"自動発注" は無人で発注確定まで行うべきでは?」→ 個店の仕入先(酒販店・卸)は電話/FAX/LINE 受注が主流で EDI 接続先が存在しないうえ、在庫データの誤り(記録漏れ・廃棄未入力)がそのまま誤発注=現金の損失になる。**完全自動発注は見送り(§4)、F-4 の「自動生成+承認+送信」に格下げして採用**。これで発注業務の所要時間は削減しつつ、誤発注リスクを承認で遮断する。
- 「リアルタイム在庫(POS 連携・重量センサー)は?」→ 個店規模では導入・保守コストが便益を大きく上回る。日次棚卸+入出庫記録の精度で発注案生成には十分。**見送り(§4)**。
- 「在庫記録は続かないのでは?(運用が破綻する典型)」→ 最大の実運用リスク。対策として入力を「入荷時にまとめて登録」「棚卸は週次でも可」の粗い粒度から始められる設計とし、発注案は在庫精度が低くても「前回発注からの経過日数」ベースの提案を併用する。この緩和策を要件に含める。

**判定:条件付き採用**(完全自動は見送り、承認付き発注案生成として採用。Phase 3)

## 3. 実装計画(フェーズ分け)

依存関係:A(基盤)と D(シフト)が B(SNS)のデータソース。F(在庫)が B の入荷情報ソース。C-3(GCP)が B の画像ホスティング前提。

### Phase 0:既存資産の改修(負債返済)— 全拡張の前提
- P-1〜P-8(§1.1)。特に Django 5.x 化、Secrets 環境変数化、タイムゾーンバグ修正、二重予約の DB 制約化。
- 既存テスト(約500行)を Django 5.x で全通過させ、リグレッションの安全網とする。

### Phase 1:店内業務のデジタル化(外部 API 非依存)
- A-1〜A-3:営業日・開店チェックリスト(自動連鎖はこの時点ではシフト確定のみ)
- D-1〜D-4:シフト・打刻・CSV・Staff 拡張
- E-1〜E-3, E-5:座席モデル・座席割当・座席ボード・業態切替
- C-3:GCP 基盤構築(Cloud Run へのデプロイ、Cloud Storage、Secret Manager)
- **この時点で外部 API が一切なくても、開店業務の省力化価値が成立する(敵対的レビューの要請:外部 API 依存機能が全滅しても投資が無駄にならない構成)**

### Phase 2:SNS 自動投稿
- B-1〜B-3, B-5:文面/画像生成・承認フロー・結果記録(まず「生成物を手動コピペ投稿」で全プラットフォーム運用開始)
- B-4:API 接続を Threads → X(有料プラン判断)→ Instagram(アプリレビュー)の順で段階投入

### Phase 3:外部連携・在庫
- F-1〜F-5:商品マスタ・入出庫・発注案生成・SNS 連動
- C-1, C-2, C-4:GBP 連携(API 承認が取れた場合のみ。取れなければ手動リマインダーに格下げ)

## 4. 見送り一覧(敵対的レビューにより実用性なしと判定)

| # | 見送った要件 | 理由 |
|---|---|---|
| R-1 | 無人での SNS 自動確定投稿 | 誤投稿(退職者掲載・顔出しNG画像)が営業被害・人格権侵害に直結。承認フローで代替 |
| R-2 | Googleマップへの空席状況リアルタイム反映 | 一般開放された API が存在しない。Reserve with Google は認定プロバイダ限定で個店は参加不能 |
| R-3 | 給与計算・労基法対応レベルの勤怠自前実装 | SaaS が月数百円/人で提供済み。法改正追従の保守を永久に負うのは費用対効果が最悪。CSV 連携で代替 |
| R-4 | グルメサイト予約在庫連携(サイトコントローラー) | API 非公開・契約コストが個店規模に見合わない。自社台帳への一元記録で代替 |
| R-5 | 座席の自動最適割当 | 十数席規模では手動割当が上回る。空き可視化と重複防止で代替 |
| R-6 | 無人の完全自動発注(EDI) | 仕入先に受け口がなく、在庫誤差がそのまま金銭損失になる。承認付き発注案生成で代替 |
| R-7 | POS・センサーによるリアルタイム在庫 | 個店規模で導入保守コストが便益を上回る。日次入出庫+棚卸で代替 |
| R-8 | 打刻の GPS 必須検証 | 小規模店では目視で足りる。オプション扱いに格下げ |

### 5.1 改修ラウンド(2026-09-01、ブランチ `claude/hardening-review-bok4kj`)

Phase 0〜3 完了後、main との全差分に対して敵対的コードレビューを実施。10件の指摘を検証し、全件対応した。

| # | 指摘 | 深刻度 | 対応 |
|---|---|---|---|
| 1 | SNS配信が AdapterError 以外の例外(生のネットワーク例外)で中断し、承認済みのまま残プラットフォームが再試行不能になる | 高 | 例外を全捕捉して失敗記録+ループ続行。承認済み下書きへの再POSTで失敗・未記録分のみ再配信する `retry_unfinished` を追加 |
| 2 | 営業時間が深夜跨ぎ(18時-翌2時)や24時超えだとカレンダー・座席ボードが500 | 高 | DB制約(開店<閉店 かつ 閉店≦24)で不正値を遮断。深夜営業の本対応は backlog C-1 として設計済み |
| 3 | 発注が一度「発注済み」になると商品が永久に再提案されなくなる | 高 | 「入荷済み」ステータス+入荷反映ボタンを追加。さらに送信後30日でブロック自動解除の安全弁 |
| 4 | 承認済みの日に再生成すると同日2件目の下書きができ二重投稿が可能 | 高 | 承認済みは再生成不可+ (store, date) のUNIQUE制約 |
| 5 | DEBUG デフォルト true・SECRET_KEY サイレントフォールバックで本番がフェイルオープン | 高 | DEBUG=false 時に開発用キーのままなら起動拒否。Dockerfile に DJANGO_DEBUG=false を焼き込み |
| 6 | ウォークイン着席が check-then-act で同時タップ時に二重着席 | 中 | 部分UNIQUE制約(座席×着席中)+IntegrityError 処理 |
| 7 | 店舗メンバー判定ヘルパーが2箇所に重複定義 | 中 | `booking/access.py` に一本化し全アプリから import |
| 8 | 在庫一覧が商品ごとに集計クエリを発行(N+1) | 中 | annotate による1クエリ化 |
| 9 | Pillow>=10.0 だとフォント無し環境のフォールバックが TypeError | 中 | Pillow>=10.1 にピン |
| 10 | 勤怠CSVが打刻1行ごとにシフトを検索(N+1) | 低 | 当月分を一括ロードして突合 |

未実装項目の棚卸しと実装前検証の結果は [backlog.md](backlog.md) を参照
(次ラウンド採用: 店長ロール・PostgreSQL対応・エラートラッキング/条件付き: 深夜営業対応・顧客向け座席予約・X画像添付・発注書PDF)。
